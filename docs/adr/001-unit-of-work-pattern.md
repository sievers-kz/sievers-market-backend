# ADR 001: Внедрение паттерна Unit Of Work (UoW)

## Status
`ACCEPTED`

## Context
**Проблема:** Изначально приложение использовало прямые запросы к репозиториям, которые оперировали общей сессией ORM, созданной на уровне DI-контейнера. Это привело к критической нестабильности в среде выполнения (runtime):
1. **Заражение сессии (Session Contamination):** При возникновении любой ошибки базы данных (например, `IntegrityError` или тайм-аут) сессия ORM помечалась как "загрязненная" (tainted/expired).
2. **Нестабильность Приложения:** Из-за переиспользования этой зараженной сессии последующие запросы к базе данных становились невозможными, что приводило к каскаду ошибок и требовало перезапуска всего запроса/процесса.
3. **Нарушение DRY:** Для восстановления стабильности требовался явный вызов `rollback()` в каждом репозитории или Use Case при возникновении ошибки. Это создавало дублирование кода и нарушало принцип DRY (Don't Repeat Yourself).

Таким образом, отсутствие централизованного управления сессией сделало невозможным корректную обработку ошибок и нарушило базовую стабильность приложения.

## Decision
Внедрить паттерн **Unit Of Work (UoW):** с использованием **контекстного менеджера** для централизации управления жизненным циклом сессии и транзакций.

1. **SQLAlchemyUnitOfWork**: в инфраструктурном слое модуля `shared` был создан базовый класс `SQLAlchemyUnitOfWork` для
централизации управления сессией базы данных. Класс имеет переиспользуемые методы `commit()`, `rollback`.
2. **Распределенные классы Unit of Work**: каждый bounded context имеет свой собственный класс UoW, который наследует
базовый `SQLAlchemyUnitOfWork`. Репозитории экспонируются как свойства UoW, гарантируя единую сессию для всех операций в рамках одной транзакции.
3. **Интеграция:** Каждый Use Case принимает UoW своего bounded context как зависимость и выполняет все операции внутри
блока `async with uow:`. Это гарантирует что Use Case работает исключительно с репозиториями своего контекста, не имея доступа к данным других контекстов.

## Consequences
**Positive:**
-   **Критическая Стабильность:** Полностью устранена проблема заражения сессии, что делает приложение устойчивым к сбоям БД и ORM.
-   **Централизация Logic:** Логика управления транзакциями (`commit`/`rollback`) полностью изъята из юзкейсов и репозиториев и централизована в UoW, соблюдая принцип DRY.
-   **Гарантия Атомарности:** Обеспечивается, что все операции в рамках юзкейса либо фиксируются, либо откатываются целиком.

**Negative:**
-   **Больше Boilerplate:** каждый bounded context требует собственного класса UoW, что увеличивает количество файлов пропорционально числу контекстов.
-   **DI Complexity:** Требуется более сложная настройка контейнера DI для корректной передачи UoW в юзкейсы.
