# ADR 003: Role-by-Existence — определение ролей через факт существования записи

## Status
`ACCEPTED`

## Context
При проектировании системы управления пользователями возникла необходимость
разграничить роли: покупатель (Customer), продавец (Vendor), администратор (Admin).

Ключевые требования:
- **Роль несёт данные:** Vendor - это не метка, это `shop_name`, `tax_id`,
  `legal_form`, `contact_fullname`, `contact_phone`.
  Customer — это минимальный профиль: fullname и аватар. Роль и её данные должны жить вместе.
- **Независимые жизненные циклы:** возможность заблокировать Vendor не затрагивая
  Customer того же аккаунта.
- **Чистота IAM:** контекст аутентификации не должен знать о бизнес-ролях -
  KYB верификация, KGD проверка контрагентов, управление листингами не его зона
  ответственности.

## Alternatives

### 1. `role` enum в таблице `accounts` `Rejected`
**Причины отказа:**
- Один аккаунт не может быть одновременно Customer и Vendor;
- При расширении ролей enum растёт по экспоненте (`VENDOR_BANNED`, `CUSTOMER_VERIFIED` и др.);
- Данные роли (shop_name, tax_id) всё равно хранятся отдельно - связь между
  ролью и её данными неявная.

### 2. `roles: list[str]` в таблице `accounts` `Rejected`
**Причины отказа:**
- Список ролей и данные роли хранятся в разных местах - нужна синхронизация;
- Гранулярное управление (заблокировать только Vendor) требует дополнительных
  флагов типа `is_vendor_banned`;
- IAM вынужден знать о бизнес-ролях чтобы корректно формировать список.

## Decision
Роль пользователя определяется **фактом существования записи** в соответствующей
таблице: `vendors`, `customers`, `admins`. Токен содержит только `account_id`.
Каждый защищённый эндпоинт самостоятельно выполняет lookup: например,
`get_current_vendor(account_id)` → `None` → 403.

**Обоснование:**
1. **Роль рядом с данными:** таблица `vendors` содержит и факт роли, и все
   её атрибуты — не нужно ходить в несколько таблиц;
2. **Гранулярное управление:** можно заблокировать Vendor (`VendorStatus.BANNED`)
   не затрагивая Customer того же аккаунта — независимые жизненные циклы;
3. **IAM остаётся чистым:** контекст IAM занимается исключительно аутентификацией.
   Бизнес-логика ролей инкапсулирована в соответствующих bounded context'ах;
4. **Потенциал выделения:** IAM как чистый контекст без бизнес-ролей потенциально
   выносится в отдельный сервис (аналог Keycloak) без переписывания остальной системы.

## Consequences
**Positive:**
- **Cohesion:** данные роли и сама роль находятся в одной таблице;
- **Гибкость управления:** независимая блокировка, верификация и управление
  жизненным циклом каждой роли;
- **Чистые границы контекстов:** IAM не засорён бизнес-логикой, каждый
  bounded context владеет своей ролью;
- **Горизонтальное расширение:** добавление новой роли не требует изменения
  существующих таблиц - создаётся запись в новой таблице. Например, Customer
  становится Vendor через `RegisterVendorUseCase` без модификации `accounts`
  или `customers`.

**Negative:**
- Определение ролей требует lookup в нескольких таблицах. JWT claims могли бы устранить лишние запросы, но вносят проблему
актуальности данных - заблокированный Vendor остаётся валидным до истечения токена без дополнительного механизма инвалидации.
