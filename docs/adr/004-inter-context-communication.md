# ADR 004: Межконтекстное взаимодействие через публичные сервисы

## Status
`ACCEPTED`

## Context
Bounded context'ы системы изолированы — каждый имеет собственный UoW,
репозитории и доменные модели. Однако ряд операций затрагивает несколько
контекстов одновременно.

Пример: закрытие профиля Vendor (`CloseVendorUseCase`) — если у аккаунта
нет записи в `customers`, её необходимо создать, чтобы аккаунт не остался
без активной роли. Vendor context не должен знать о внутреннем устройстве
Customer context'а.

## Alternatives

### 1. Прямой доступ к репозиторию чужого контекста `Rejected`
**Причины отказа:**
- Vendor context получает доступ к внутренностям Customer — его репозиторию,
  UoW, доменным моделям;
- Любое изменение внутри Customer context'а потенциально ломает Vendor;
- Нарушается изоляция bounded context'ов.

### 2. Domain Events + Message Broker (RabbitMQ) `Rejected`
**Причины отказа:**
- Концептуально верно для микросервисной архитектуры, но избыточно для
  модульного монолита на текущей стадии;
- Требует настройки брокера, Outbox паттерна и Saga для компенсации ошибок;
- Overhead несоразмерен задаче.

## Decision
Взаимодействие между bounded context'ами осуществляется через **публичные
сервисы** — классы уровня Application, которые скрывают внутреннюю реализацию
контекста за публичным контрактом.

Пример: `CloseVendorUseCase` принимает `CustomerService` как зависимость
через DI (`providers.Dependency()`). Vendor context знает только публичный
метод `CustomerService.create()` — внутренние детали (UoW, репозиторий,
доменная модель Customer) скрыты.

**Обоснование:**
1. **Изоляция:** Vendor context не зависит от внутреннего устройства Customer —
   только от публичного контракта сервиса;
2. **Устойчивость к изменениям:** внутренняя реализация Customer context'а
   может меняться без влияния на Vendor, пока контракт сервиса стабилен;
3. **Соразмерность:** решение не требует дополнительной инфраструктуры —
   достаточно DI контейнера который уже в стеке.

## Consequences
**Positive:**
- **Чёткая граница:** Vendor context взаимодействует с Customer исключительно
  через публичный контракт, не имея доступа к его репозиториям и доменным моделям;
- **Простота:** взаимодействие реализуется прямым вызовом метода без
  дополнительной инфраструктуры.

**Negative:**
- **Нет распределённой транзакции:** операции в разных контекстах выполняются
  в отдельных транзакциях. Если `CustomerService.create()` падает после коммита
  Vendor — аккаунт остаётся без активной роли. Решается через Outbox + Saga,
  отложено до пост-MVP;
- **Конкретный класс вместо интерфейса:** `CustomerService` инжектируется
  как конкретная реализация, а не абстракция — при необходимости замены
  потребует изменения зависимостей.
