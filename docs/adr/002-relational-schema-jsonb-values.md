# ADR 002: Реляционная схема атрибутов и JSONB для значений (отказ от EAV)

## Status
`ACCEPTED`

## Context
При проектировании системы возникла необходимость хранить динамический набор атрибутов
для подкатегорий (Тракторы, Комбайны, Автотранспорт и др.). У каждой подкатегории свой
набор характеристик, и он меняется со временем.

Требования:
- **Гибкость схемы:** возможность добавлять атрибуты без изменения SQL-схемы (без `ALTER TABLE`);
- **Управляемая схема атрибутов:** тип, варианты значений, группа, единица измерения,
  обязательность, участие в фильтрах и порядок отображения задаются администратором;
- **Переиспользование:** один и тот же атрибут (например, `engine_power`) может
  использоваться в нескольких подкатегориях;
- **Архитектурная чистота:** чёткое разделение между схемой атрибутов (каталог)
  и значениями атрибутов (листинг);
- **Минимум инфраструктуры:** решение в рамках существующего стека.

## Alternatives

### 1. EAV `Rejected`
Значения хранятся построчно в таблице вида `listing_attribute_values (listing_id, attribute_id, value)`.

**Причины отказа:**
- Сложные многоуровневые JOIN при получении атрибутов листинга;
- Отсутствие типизации значений на уровне БД: все значения хранятся как VARCHAR,
  либо нужна отдельная колонка на каждый тип;
- Фильтрация по нескольким атрибутам превращается в набор self-JOIN или подзапросов.

### 2. Схема атрибутов в JSONB у подкатегории `Superseded`
Прежний вариант этого ADR: подкатегория хранит описание своих атрибутов как JSON-документ.

**Причины отказа:**
- Нет ссылочной целостности: группы и единицы измерения не связаны внешними ключами;
- Нет уникальности ключа атрибута: один и тот же `key` может быть описан по-разному
  в разных подкатегориях;
- Атрибут нельзя переиспользовать: описание дублируется в каждой подкатегории;
- Неудобно администрировать: стандартные инструменты показывают сырой JSON.

### 3. MongoDB `Rejected`
**Причины отказа:**
- Отсутствие реляционных связей и UUID-типизации усложняет интеграцию
  с существующей реляционной схемой;
- Лишняя инфраструктура: PostgreSQL покрывает все требования.

## Decision
Использовать **гибридную модель**: конфигурация атрибутов хранится в реляционных таблицах,
а значения, введённые пользователем, хранятся в JSONB.

**Схема атрибутов** (контекст `catalog`, `src/core/catalog/infrastructure/models.py`):
- `attribute_definitions`: определение атрибута: уникальный `key`, `label`, `type`
  (`string`, `integer`, `float`, `boolean`, `enumerate`, `reference`), `options`
  (варианты для `enumerate`), `source` (справочник для `reference`);
- `attribute_groups`: группы атрибутов для отображения (`key`, `label`, `position`);
- `unit_of_measure`: единицы измерения (`key`, `label`);
- `subcategory_attributes`: связь many-to-many между подкатегорией и определением атрибута.
  Хранит метаданные использования: `group_id`, `unit_id`, `required`, `filterable`, `position`.

**Значения атрибутов** (контекст `listing`): колонка `listings.attributes` типа JSONB.
Ключами служат `attribute_definitions.key`, например `{"engine_power": 123}`.

**Обоснование:**
1. **Гибкость схемы:** новый атрибут добавляется строками в `attribute_definitions`
   и `subcategory_attributes`, без миграции схемы БД;
2. **Целостность конфигурации:** внешние ключи, уникальность `key` и типизированные колонки
   гарантируют корректность схемы атрибутов на уровне БД;
3. **Архитектурное разделение:** каталог владеет схемой атрибутов, листинг хранит только значения;
4. **Простота чтения значений:** атрибуты листинга извлекаются вместе с листингом, без JOIN;
5. **PostgreSQL уже в стеке:** решение не требует дополнительной инфраструктуры.

**Валидация и поиск:**
- При создании листинга и изменении атрибутов значения проверяются
  `AttributeValidationService` (`src/core/catalog/infrastructure/attribute_validation.py`):
  по `subcategory_attributes` строится динамическая Pydantic-модель, которая учитывает
  тип и обязательность каждого атрибута;
- Фильтрация по значениям атрибутов выполняется в Meilisearch: атрибуты с `filterable = true`
  добавляются в filterable-поля индекса `listing` (`ListingSearchService.sync_schema`).

## Consequences
**Positive:**
- **Гибкость:** новые атрибуты подкатегорий добавляются данными, без миграций схемы БД;
- **Переиспользование:** одно определение атрибута подключается к нескольким подкатегориям
  с разными группой, единицей измерения и обязательностью;
- **Целостность схемы:** конфигурация атрибутов защищена ограничениями БД;
- **Динамические формы:** клиент строит форму листинга и фильтры по данным
  `subcategory_attributes`;
- **Простота запросов:** значения атрибутов листинга читаются одним запросом без JOIN.

**Negative:**
- **Смещение валидации значений:** типы и структура значений в JSONB не гарантируются
  на уровне БД. Корректность обеспечивает только приложение;
- **Рассинхронизация схемы и данных:** при переименовании или удалении `key`, а также при смене
  типа атрибута в `listings.attributes` остаются устаревшие значения. Их нужно
  мигрировать данными;
- **Зависимость фильтрации от поискового индекса:** PostgreSQL не индексирует `listings.attributes`,
  поэтому фильтрация по атрибутам опирается на Meilisearch и требует синхронизации индекса.
